# Higher Level Primitives

Primitives are an interesting concept.

In our programming languages we have `char`, `int`, `float`, `boolean`. Perhaps some others I'm forgetting.

We take these primitives and we compose them into structs. We take those structs and compose them again. We take statements: `if`, `for`, `while`, and compose them into functions and we take functions and compose them into systems.

Each of these layers are themselves a primitive: functions are a primitive especially if your language can pass functions as arguments.

Each layer is a primitive and I need some of a higher level.

My professional workflow involves JIRA, Aasana, GitHub, and a few other enterprise tools. You are all, like me, too familiar with these.

## CLIs

Some higher level primitive's I've found are CLIs that allow me, and more importantly AI, to interact with each of these systems but I've found most CLIs both, paradoxically, too powerful and too complex.

I use the open source JIRA CLI tool. This tool does everything I need and I can toss it to claude or codex to manage my tickets but sometimes I want to be able to just do what needs to be done quickly and easily. I may need to assign a bunch of tickets to myself, add a label, move them from `'To Do'` to `'In Progress'`, and thow in a comment or two on some. Remembering all the commands, flags, ticket numbers, and everything else is a feat in which I have no interest in achieving. I don't have it in me nor do I don't want to.

I need a higher level primitive:

A CLI is a great start because it provides a programmatic interface into the system. An API does the same. Both get us the data we need to then process and render how we want.

Just as an API can have hundreds of endpoints, so too can a CLI have hundreds of commands... 👀 kubectl in particular comes to mind.

What I want instead is some sort of UI with the speed and precision of a CLI but with a bit more visual support to understand the actions I can take and the entities against them I can take.

What I want is a TUI!

## TUIs

My background is as a front end developer. Frontend is fascinating. We interact with the same sort of problems as other software domains but on a smaller scale. Principly though the problems are the same: Race conditions, managing concurrency, coordinating state updates, cache invalidation, performance etc.

Front end though is more than web apps. It's more than mobile apps. Frontend is also the CLI. It is also the TUI. On the web, a frontend engineer's best friend is React. And really at its core React is a scheduler, and differ for a state management system: state changes, React determines what parts of the UI have changed, and schedules those parts to rerender.

React is great though for a number of reasons. It provides a phenomenal developer experience. React and its toolchain provide Hot Module Reloading, great developer tools for introspection, a test framework, an ecosystem for exceptional dependencies, and everything else that comes with a great language and runtime. And all for if not free, extremely low cost.

Wouldn't it be cool to update a code base for a TUI and seeing the live running instance display the change immediately and automatically. It would feel surreal, until it becomes expected.

React is not just for the web, these capabilities are generic.

TUI's are also a frontend, we would just need a good component library to express rich and performant user interfaces... something like [ink](https://github.com/vadimdemedes/ink)! Ink is a React component library for terminal environments. Its a TUI component library!

But a lot of React web apps have learned how we often want to store our server state separately from our frontend state and that we want to have metadata about our server state and keep track of the metadata of actions against our server state. Luckily the frontend ecosystem received [TanstackQuery](https://tanstack.com/query/latest) and all our work became easier.

These are a wonderful set of primitives to build what I want, but its not yet what I actually want.

## JIRA TUI

I want a JIRA TUI.

So we can take the JIRA cli tool, create some typescript functions to progrmattically invoke it, capture the reponse, which is kindly made available as JSON, chuck the JSON into our TanstackQuery cache, compose Ink components for our UI, manage some frontend state with React, and build a fully fledged TUI with all the niceties of a modern web app.

We can also leverage the environment and delegate functions to other CLI tools IE FZF for fuzzy finding in a menu or ripgrep for searching.

A flow I want to easily support is something like: select a JIRA board, filter to the tickets assigned to me, select a few of those, and update their status from `'To Do'` to `'In Progress'`. I want to be able to do this quickly, and I don't want to memorize a bunch of commands or ticket numbers. I want a previous step to carry forward into the next reducing to some final selection of entities against which I then take some action.

Another flow might be to select an epic and create a bunch of tickets, with all the required fields prefilled, in this selected epic. I don't want to create the tickets one by one. I may have 12 tickets I want to get added and I want to create and add them just by writing down each ticket's title on a new line. For some I may even want to include a description.


## Wrapping Up
These are the capabilties I want in the primitives of my workflow: discoverable and batch oriented actions. And I think this is what most users want from their tools.

So finally we have arrived at the primitive I want. It's a very high level one, built on many smaller primitives with each composed with its neighbors. Because, really, what is an `int` but a composition of a handful of bits.
